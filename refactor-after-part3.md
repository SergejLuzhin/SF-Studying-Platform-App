## Границы и правила

- Использовать Java 23, Maven и PostgreSQL. Обычный тестовый профиль использует Testcontainers; `create-drop` допустим только в отдельной тестовой БД. **Не запускать тесты с `create-drop` на рабочей базе `studying_platform_v2`.** Не менять рабочие данные и схему без отдельного согласия пользователя.
- Исправлять выявленные ошибки и необходимые для них тесты; не реализовывать демоданные, CI, Docker Compose или другие будущие этапы.
- Аутентификация и авторизация не входят в проект. Проверка бизнес-роли преподавателя не удостоверяет личность вызывающего клиента. Удаление `isCorrect` из ответа для прохождения теста не делает административные эндпоинты защищёнными: без аутентификации они доступны всем, кто может обратиться к API.
- Пути существующих эндпоинтов сохранять. Изменения ответов и входных DTO, описанные ниже, необходимы для исправления некорректного API; обновлять все тесты и документацию в той же работе. Не менять публичные контракты без необходимости.
- Все созданные или изменённые Java-классы и методы, включая конструкторы, приватные и тестовые методы, снабжать содержательным JavaDoc на русском. Идентификаторы — на английском. Не переписывать несвязанные файлы ради JavaDoc.
- Перед каждым пунктом проверять `git status --short`, читать затрагиваемые файлы и сохранять чужую работу. На момент составления плана в дереве присутствует неотслеживаемый `stages/stage-21.md`: не удалять и не перезаписывать его без отдельной просьбы пользователя.
- Этапы общего плана не перенумеровывать. Этот документ выполняется самостоятельно, не является вызовом `/execute-stage`. Существенные архитектурные решения оформлять согласно правилам ADR проекта; на момент составления плана принятых ADR в индексе нет.
- Для каждого пункта фиксировать фактические результаты `PASS`, `FAIL` или `NOT_RUN`. Если Docker или JDK 23 недоступны, не подменять PostgreSQL на H2 и не объявлять проверку пройденной. После работы обновить `state.md` как короткий checkpoint.
