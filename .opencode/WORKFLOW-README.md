# OpenCode: один этап одной командой

Комплект предназначен для **небольшого проекта с одной текущей задачей**. Никаких папок `feature-*`: только общий план и подробные планы этапов.

## Как установить

1. Распакуй **содержимое архива прямо в корень Git-проекта**, сохранив пути папок. Если `AGENTS.md` или `.opencode/*` уже существуют, **сначала сравни и объедини конфигурации**: не перетирай собственные настройки.
2. В корне должны быть твои `task.md` (требования) и `plan.md` (общий план). **Они не включены в архив, чтобы не затереть существующую задачу.** `state.md` появится после первого этапа.
3. Для общего плана используй нумерацию и статусы, например:

```md
# План

## Stage 01: Подготовить инфраструктуру
Status: pending
Acceptance: инфраструктура работает, тесты проходят.

## Stage 02: Реализовать бизнес-логику
Status: pending
Acceptance: положительные и отрицательные сценарии покрыты тестами.
```

4. Запусти OpenCode в корне проекта и введи:

```text
/execute-stage
```

## Что произойдёт

1. `stage-executor` определит один следующий этап.
2. `stage-planner` изучит код и **индекс `docs/adr/README.md`**, создаст/обновит `stages/stage-XX.md`. Реализатор дождётся результата планировщика и заново прочитает детальный план.
3. Реализатор внесёт необходимые изменения и тесты.
4. `stage-tester` независимо проверит этап. При дефектах реализатор проведёт не более двух циклов исправления и повторной проверки.
5. Реализатор обновит `plan.md` и `state.md`, а при любом создании или изменении ADR **обязательно синхронизирует `docs/adr/README.md`**.
6. Завершит работу **без Git-коммита**. Следующий этап запускается отдельной командой после твоей проверки.

## Архитектурные решения

- `docs/adr/README.md` уже присутствует, но индекс пуст: решения надо добавлять только по мере возникновения.
- Для существенных архитектурных вопросов реализатор может подготовить ADR в статусе `Proposed` и обновить индекс, затем остановиться для согласования.
- Ни планировщик, ни реализатор не утверждает ADR (`Accepted`) без явного разрешения пользователя.
- Изменение статуса и замена ADR также должны отражаться в индексе.

## Конфигурация и безопасность

- Дополнительные Git-запреты находятся в `.opencode/opencode.jsonc`, **не в корневом `opencode.jsonc`**, чтобы не перезаписывать существующие настройки локальной модели/провайдера.
- При существующем `.opencode/opencode.jsonc` объедини секцию `policies` вручную; не заменяй свой файл вслепую.
- Конфигурация ориентирована на актуальный **OpenCode V2** (`permissions`, `policies`, `subagent`). В OpenCode V1 нужны другие имена настроек.
- Shell-политики — защита от обычных команд, но не полноценный security sandbox. Не запускай непроверенные shell-скрипты от имени агента.
- Субагенты работают в отдельных контекстах; главный агент обязан дождаться их финального результата. Надёжность соблюдения инструкции зависит также от возможностей локальной LLM.
- Не считай этап завершённым, если обязательные тесты не были реально выполнены.

## Расположение файлов

```text
project/
├── AGENTS.md
├── task.md                     # Твой файл, в архиве отсутствует
├── plan.md                     # Твой файл, в архиве отсутствует
├── state.md                    # Создаст реализатор
├── stages/                     # Подробные планы stage-XX.md
├── docs/
│   └── adr/
│       ├── README.md           # Автоматически поддерживаемый индекс
│       └── NNNN-short-title.md # Создаётся по необходимости
└── .opencode/
    ├── opencode.jsonc          # Git-политики
    ├── WORKFLOW-README.md      # Этот файл
    ├── commands/
    │   └── execute-stage.md
    └── agents/
        ├── stage-executor.md
        ├── stage-planner.md
        └── stage-tester.md
```
