# Правила проекта для ИИ-агентов

## 1. Язык и оформление кода

- **Все ответы пользователю — на русском языке:** вопросы, пояснения, отчёты и результаты работы.
- **Для каждого Java-класса и Java-метода, который создаёшь или изменяешь, обязателен содержательный JavaDoc на русском языке.** Правило распространяется также на интерфейсы, `enum`, `record`, конструкторы, `private`-методы, методы с `@Override`, тестовые классы и тестовые методы. Поддерживай имеющийся JavaDoc в актуальном состоянии. Не переписывай несвязанные файлы только ради дополнения JavaDoc.
- В JavaDoc при необходимости используй `@param`, `@return`, `@throws`; названия параметров и типов должны совпадать с кодом и оставаться английскими.
- **Все программные идентификаторы — только на английском:** имена пакетов, классов, интерфейсов, методов, переменных, параметров, полей, констант, тестов и файлов исходного кода. Запрещены кириллица и русская транслитерация в идентификаторах.
- Документацию и JavaDoc пиши на русском. Тексты пользовательского интерфейса выбирай согласно локализации проекта; не меняй публичные API-контракты ради языкового правила.
- Соблюдай существующие стиль, соглашения, архитектуру и форматирование проекта.

## 2. Git и безопасность

- **Не выполняй самостоятельно `git add`, `git commit`, `git push`, создание тегов, переписывание Git-истории или разрушительные Git-команды.** Пользователь самостоятельно проверяет изменения, индексирует их и делает коммиты.
- Можно использовать безопасные команды чтения: `git status`, `git diff`, `git log`, `git show`.
- Не перезаписывай и не удаляй несвязанные пользовательские изменения. Проверяй рабочее дерево перед началом этапа.
- Не устанавливай зависимости, не удаляй файлы и не меняй публичные контракты без необходимости; потенциально разрушительные операции согласовывай.
- Делай минимальные изменения, относящиеся к текущему этапу. Не выполняй попутный рефакторинг.

## 3. Документы и планирование

- В проекте одна текущая задача, без деления на отдельные фичи и каталоги задач.
- `task.md` (корень) — требования и критерии приёмки текущей задачи.
- `plan.md` (корень) — **общий** план со списком этапов и их статусами.
- `stages/stage-XX.md` — **подробный** план одного этапа. Создавай его непосредственно перед выполнением этапа, не планируй будущие этапы детально заранее.
- `state.md` (корень) — короткий актуальный checkpoint для продолжения в новой сессии. Обновляй после работы над этапом; не превращай в накопительный журнал.
- Для статусов этапов используй `pending`, `in_progress`, `completed`, `blocked`. Номер этапа сохраняй неизменным.
- При поиске информации предпочитай адресный поиск и чтение релевантных файлов. Не загружай в контекст весь репозиторий или огромные логи без необходимости.

## 4. Архитектурные решения (ADR)

- ADR размещаются по одному решению в файле `docs/adr/NNNN-short-title.md`.
- **`docs/adr/README.md` — обязательный актуальный индекс всех ADR.** При создании, изменении статуса, переименовании или замене ADR в этой же работе обновляй соответствующую запись индекса. Индекс должен содержать ID, название со ссылкой, статус и область решения; не добавляй вымышленные ADR.
- Если индекса нет, создай его при создании первого ADR. Если индекс существует, не удаляй его и поддерживай согласованность с фактическими файлами.
- Перед планированием этапа сначала прочитай индекс, затем — только относящиеся к этапу ADR со статусом `Accepted`. `Proposed` не является утверждённым ограничением.
- Создавай ADR только для **существенных** архитектурных решений, а не для каждого этапа или мелкой детали реализации.
- Новое решение оформляй со статусом `Proposed`. **Не переводи его в `Accepted` без явного согласования пользователя.** Если согласование требуется для реализации, останови этап, зафиксируй блокер и предложи решение пользователю.
- Для замены принятого решения создавай новый ADR; прежний сохраняй со статусом `Superseded`, со ссылкой на замену. Обновляй обе записи индекса. `Rejected` и `Superseded` сохраняй в истории, не удаляй.
- Не нарушай принятые ADR молча. При противоречии между ADR и новой задачей сообщи о конфликте и запроси решение.

## 5. Протокол выполнения этапа

- Один вызов `/execute-stage` выполняет **ровно один** очередной этап из `plan.md`.
- Сначала дождись завершения субагента `stage-planner`, затем прочитай с диска его `stages/stage-XX.md`; не начинай реализацию раньше этого.
- При необходимости предварительного архитектурного согласования подготовь `Proposed` ADR, обнови индекс и приостанови реализацию до решения пользователя.
- Реализуй только текущий этап и добавь релевантные автоматизированные тесты (для исправления дефекта — регрессионный тест, если применимо).
- После реализации обязательно вызови **отдельного субагента** `stage-tester` и дождись его отчёта. Если найдены дефекты — не более двух циклов «исправление → повторное тестирование».
- Статус проверок обозначай честно: `PASS`, `FAIL`, `NOT_RUN`. Нельзя объявлять обязательную проверку пройденной, если она не была выполнена.
- Ставь этапу `completed` только после соблюдения критериев приёмки и успешных обязательных проверок; иначе используй `in_progress` или `blocked` с указанием причины.
- Обновляй `state.md` и `plan.md` после работы. В финальном отчёте укажи изменённые файлы, проверки, открытые проблемы и необходимые действия пользователя. **Никаких Git-коммитов.**
