# План исправлений после проверки этапов 01–08

## Цель

Устранить выявленные при проверке расхождения первых восьми этапов с `plan.md`, `task.md` и `task-part2.md`, не переходя к разработке функциональности этапа 09. Каждый шаг ниже рассчитан на небольшую самостоятельную работу и включает проверки. Номера этапов основного плана не меняются.

## Исходные данные и ограничения

- При проверке `mvn verify` все 69 существующих тестов прошли. Стандартный запуск выполнял 63 теста на H2 и 6 на PostgreSQL через Testcontainers. При отдельном запуске с принудительной PostgreSQL существующие тесты также прошли, но не покрыли все проблемные сценарии.
- На PostgreSQL с Java 23 отдельно воспроизведены `LazyInitializationException` при использовании списков после завершения транзакции и ошибка ограничения уникальности при повторной записи после отписки.
- Согласованные правила сохраняются: один студент может записаться на конкретный курс только один раз; отписка переводит запись в архивное состояние и не удаляет учебную историю; пароль и механизмы безопасности не входят в проект.
- PostgreSQL и Docker обязательны для интеграционных проверок; используем Java 23. Разработка и тесты не должны подключаться к рабочей базе по ошибке.
- Не добавлять функциональность заданий, полноценное удаление учебной истории, REST API или другие возможности будущих этапов. Не включать аутентификацию, авторизацию и хранение паролей.
- Все создаваемые или изменяемые Java-классы и методы сопровождаются содержательным JavaDoc на русском. Идентификаторы — на английском.
- Перед работой проверить `git status`, актуальные `plan.md`, `state.md`, этот документ и индекс ADR. Не удалять и не перезаписывать чужие изменения. При необходимости существенного архитектурного решения действовать по правилам ADR и согласования из `AGENTS.md`.
- После изменения схемы Hibernate с `ddl-auto=update` не гарантирует удаление старых колонок и ограничений. Не удалять данные и не изменять существующую базу разрушительным способом без явного согласия пользователя; тесты используют отдельную одноразовую базу.
- При необходимости выполнения через `/execute-stage` соблюдать проектный протокол: отдельный подробный план текущего этапа от `stage-planner`, затем независимая проверка `stage-tester`; не объявлять проверки пройденными без их фактического запуска.

**Критерии и проверки:**

- Docker и доступность образа PostgreSQL являются обязательными условиями запуска; если они недоступны, проверка — `NOT_RUN` или `FAIL` с причиной, а не `PASS`.
