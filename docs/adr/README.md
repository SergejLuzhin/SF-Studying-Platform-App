## Правила ведения

1. Каждое значимое решение хранится в собственном файле `NNNN-short-title.md`.
2. При **создании ADR**, **смене статуса**, **переименовании** или **замене решения** в той же операции создай или обнови запись индекса. Название решения должно ссылаться на реальный Markdown-файл относительно этого каталога.
3. Допустимые статусы: `Proposed`, `Accepted`, `Rejected`, `Superseded`.
4. Статус `Accepted` устанавливается **только после явного согласования пользователя**.
5. Устаревшие ADR сохраняются. Для `Superseded` укажи в соответствующих документах ссылку на новый ADR.
6. Перед планированием этапа прочитай индекс и открой лишь **релевантные `Accepted` ADR**. `Proposed` — предложение, а не действующее правило.
7. ADR не требуется для каждого этапа: оформляй только существенные архитектурные решения, у которых есть долгосрочные последствия.

## Минимальные разделы нового ADR

- Заголовок: `ADR-NNNN: <решение>`.
- `Status`, `Date`.
- `Context` — проблема и ограничения.
- `Decision` — что предлагается или принято.
- `Alternatives` — существенные альтернативы.
- `Consequences` — плюсы, риски и ограничения.
- `Related` — ссылки на связанные ADR, этапы и требования при наличии.
