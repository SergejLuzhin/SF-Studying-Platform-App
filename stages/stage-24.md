# Этап 24. Итоговая проверка (Final Check)

**Статус:** `completed`
**Приоритет:** Высок

## 1. Цель этапа

Провести финальную валидацию учебного проекта «Studying-Platform» перед сдачей. Необходимо убедиться, что весь функционал реализован в соответствии с требованиями `task.md` и `task-part2.md`, сборка стабильна, тесты проходят, а документация соответствует коду.

**Ключевые задачи:**
1.  Успешный прогон полного набора тестов (unit, integration, HTTP).
2.  Проверка сквозного сценария (E2E) от создания курса до результата теста.
3.  Убедиться в отсутствии `Open Session in View` и корректной работе ленивой загрузки.
4.  Проверить генерацию JavaDoc и инструкции по запуску.

## 2. Связанные файлы и ADR

*   **Исходный код:** `src/main/java/com/studying/platform/` (пакеты `model`, `repository`, `service`, `controller`).
*   **Конфигурация:** `pom.xml`, `src/main/resources/application.yml`, `application-dev.yml`, `application-test.yml`.
*   **Тесты:** `src/test/java/com/studying/platform/` (включая `RestAcceptanceTest.java`, `MvpFlowTests.java`, `PartTwoAcceptanceTests.java`).
*   **Документация:** `README.md`, `docs/adr/README.md` (индекс пуст, конфликтов с ADR нет).
*   **Требования:** `task.md`, `task-part2.md`.

## 3. План действий

### Шаг 1: Подготовка окружения
1.  Убедиться, что Docker-контейнеры (включая тестовые Testcontainers) не конфликтуют с текущим рабочим окружением.
2.  Выполнить полную очистку артефактов:
    ```bash
    mvn clean
    ```

### Шаг 2: Компиляция и генерация JavaDoc
1.  Скомпилировать проект:
    ```bash
    mvn -B compile
    ```
2.  Сгенерировать JavaDoc для основного и тестового кода, зафиксировать предупреждения:
    ```bash
    mvn -B javadoc:javadoc javadoc:test-javadoc
    ```
    *Примечание: Предупреждения JavaDoc не являются ошибкой сборки, но должны быть зафиксированы в отчёте.*

### Шаг 3: Запуск полного набора тестов
1.  Запустить полный цикл проверки (компиляция + unit + integration + HTTP-тесты с Testcontainers):
    ```bash
    mvn -B verify
    ```
2.  Проверить отчёт `target/surefire-reports/` и `target/failsafe-reports/` на наличие ошибок или пропусков.
3.  Ожидаемый результат: 0 ошибок, 0 пропусков.

### Шаг 4: Проверка сквозного сценария (E2E)
1.  **Автоматизированная проверка:** Убедиться, что тесты `RestAcceptanceTest.java`, `MvpFlowTests.java` и `PartTwoAcceptanceTests.java` проходят успешно, так как они реализуют сценарии от создания сущностей до получения результатов.
2.  **Ручная проверка (curl):**
    *   Запустить приложение (профиль `dev`): `mvn spring-boot:run -Dspring-boot.run.profiles=dev`
    *   Выполнить последовательность:
        1.  Создать пользователя-студента и преподавателя.
        2.  Создать курс с категорией.
        3.  Добавить модуль и урок.
        4.  Создать задание и отправить решение.
        5.  Создать тест и пройти его.
        6.  Проверить наличие результата (`QuizSubmission`).
    *   Убедиться, что при обращении к связанным коллекциям (`modules`, `lessons`) вне транзакции возникает `LazyInitializationException` (если не используется `JOIN FETCH` в контроллерах), подтверждая правильную настройку ленивой загрузки.

### Шаг 5: Проверка конфигурации (Open Session in View)
1.  Проверить файлы `src/main/resources/application-*.yml`.
2.  Убедиться, что параметр `spring.jpa.open-in-view` явно установлен в `false` или отсутствует (так как по умолчанию в Spring Boot 3.x он отключён, но лучше явно зафиксировать настройку, если это требуется для обучения).
3.  Убедиться, что в тестах (`@SpringBootTest`) используется изолированная база (Testcontainers JDBC URL).

### Шаг 6: Сверка с критериями оценивания
1.  Проверить наличие всех 15-20 сущностей из `task.md`.
2.  Проверить реализацию REST API для ключевых сущностей (`/api/courses`, `/api/users`, `/api/quizzes` и т.д.).
3.  Проверить `README.md` на наличие инструкций для запуска, переменных окружения и примеров `curl`.

## 5. Затронутые файлы

В рамках *проверки* файлы не изменяются. В случае обнаружения ошибок (блокирующих тесты или инструкции) могут быть исправлены:
*   `src/main/resources/application.yml` (если нужно явно отключить OSIV).
*   `README.md` (если инструкции устарели).
*   Файлы тестов (`src/test/java/...`), если нужно добавить недостающие сценарии E2E.

## 6. Риски и ограничения

1.  **Отсутствие Docker:** Если Docker не запущен, Testcontainers (и связанные интеграционные тесты) упадут. Необходимо убедиться в доступности Docker-демона.
2.  **Конфликт портов:** Локальный порт для базы данных может быть занят.
3.  **Время выполнения:** Полный прогон `mvn verify` может занять значительное время из-за поднятия контейнеров.

## 7. Отчёт

После выполнения этапов заполнить таблицу статусов выше и указать:
*   Финальное количество пройденных тестов.
*   Список предупреждений JavaDoc (если есть).
*   Скриншот или лог успешного E2E сценария.
*   Подтверждение, что проект готов к публикации в репозитории.
