# Этап 20: Ленивая загрузка и сквозной CRUD

## Цель этапа

Демонстрация и верификация корректного поведения ленивой загрузки (`Lazy Initialization`) в связке с `EntityManager` и сервисным слоем, а также проверка сквозных CRUD-операций и каскадных связей на реальной базе данных PostgreSQL (Testcontainers).

Этот этап подтверждает, что:
1. Прямое обращение к ленивым коллекциям вне транзакции (после очистки контекста сущности) вызывает `LazyInitializationException`.
2. Предусмотренный сервисный метод `CourseService.getCourseStructure(Long)` успешно возвращает полную структуру курса (модули и уроки) внутри транзакции.
3. Операции создания, чтения, изменения и удаления (CRUD) корректно работают с PostgreSQL, включая каскадное распространение изменений по связям.

## Критерии приёмки

1. Вне закрытой сессии `EntityManager` обращение к незагруженной ленивой коллекции (например, `Course.modules`) вызывает `LazyInitializationException`.
2. Предусмотренный сервисный способ (`CourseService`) возвращает нужные данные (структуру курса) без ошибки инициализации.
3. Проверены создание, чтение, изменение и удаление сущностей (`Course`, `Module`, `Lesson`) на PostgreSQL через Testcontainers.
4. Проверены каскадные операции сохранения и удаления родительских сущностей.

## Связанные файлы и ADR

- **Сущности:** `src/main/java/.../entity/Course.java` (связи `modules`, `enrollments`, `reviews`, `tags` — `LAZY`), `src/main/java/.../entity/Module.java` (`lessons` — `LAZY`), `src/main/java/.../entity/Lesson.java`.
- **Сервисы:** `src/main/java/.../service/CourseService.java` (метод `getCourseStructure`).
- **ADR:** Архитектурные решения для данного этапа не требуются (все решения по ленивой загрузке и каскадам зафиксированы в Этапе 01 и приняты).

## План реализации

### Шаг 1. Подготовка тестового класса

Создать новый тестовый класс `LazyLoadingAndCascadeTests` в пакете `src/test/java/...`.
Настроить класс для работы с Testcontainers:
- Использовать `@DataJpaTest` для загрузки только слоя JPA.
- Использовать `@ActiveProfiles("test")` для подключения к тестовой PostgreSQL.
- Добавить `@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)`, чтобы использовать Testcontainers, а не H2.
- В `@BeforeEach` вручную инициализировать зависимости (`CourseService`, репозитории) через `ApplicationContext`.

### Шаг 2. Тест демонстрации проблемы ленивой загрузки

Реализовать тест `testLazyInitializationException`:
1. Создать объект `Course` и сохранить его через репозиторий (`repository.save(course)`).
2. Вызвать `entityManager.flush()` для синхронизации с базой.
3. Вызвать `entityManager.clear()`, чтобы отделить (detach) сущность `Course` от контекста Hibernate.
4. Попытаться обратиться к ленивой коллекции `course.getModules()` (или создать пустой список и проверить загрузку).
5. **Ожидаемый результат:** Выбрасывается исключение `LazyInitializationException` (или `org.hibernate.LazyInitializationException`), содержащее сообщение о неимеющем сессии `Session`. Это доказывает, что коллекция не была загружена при `clear()`.

### Шаг 3. Тест демонстрации решения через сервис

Реализовать тест `testServiceFetchCourseStructure`:
1. Создать объект `Course`, добавить в него `Module` и `Lesson` (подготовить полную иерархию).
2. Сохранить всё через `CourseService.saveCourse(...)` (в рамках одной транзакции).
3. Вызвать `CourseService.getCourseStructure(courseId)`. Этот метод аннотирован `@Transactional`, что гарантирует работу в контексте сессии.
4. **Ожидаемый результат:** Метод возвращает `Course` (или DTO), в котором списки модулей и уроков заполнены и не вызывают исключений.

### Шаг 4. Тест каскадного сохранения (Create)

Реализовать тест `testCascadeSave`:
1. Создать иерархию: `Course` -> `Module` -> `Lesson`.
2. Вызвать `courseService.saveCourse(...)`.
3. Выполнить `entityManager.flush()`.
4. С помощью прямого SQL-запроса или выборки из репозиториев (`moduleRepository`, `lessonRepository`) убедиться, что в базе данных PostgreSQL созданы все три записи, и внешние ключи (`fk_course`, `fk_module`) проставлены корректно.

### Шаг 5. Тест каскадного удаления (Delete)

Реализовать тест `testCascadeDelete`:
1. Создать и сохранить иерархию (аналогично Шагу 4).
2. Удалить `Course` через `courseService` или `courseRepository`.
3. **Ожидаемый результат:** Записи `Module` и `Lesson` также удаляются из базы данных (проверить через количество записей или `countById`), так как для связей настроены каскады удаления (`CascadeType.REMOVE` или `CascadeType.ALL`).

### Шаг 6. Тест обновления (Update)

Реализовать тест `testCourseUpdate`:
1. Создать и сохранить `Course` с названием "Old Name".
2. Загрузить его, изменить поле на "New Name" и сохранить.
3. Проверить, что в базе данных обновилось поле `name` для данного `id`.

## Риски и ограничения

- Время старта контейнеров PostgreSQL может увеличить время сборки; использовать `--batch` при запуске.
- Убедиться, что тесты не зависят друг от друга (использовать уникальные ID или удалять данные в `@AfterEach`, хотя `@DataJpaTest` обычно оборачивает тесты транзакцией с откатом).
- Исключение `LazyInitializationException` является проверочным маркером; в продакшн-коде прямые обращения к сущностям из контроллеров без транзакции недопустимы.
